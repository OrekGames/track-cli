Do not replace `match value.to_lowercase().as_str() { ... }` (or `matches!` on a lowercased string) with chains of `eq_ignore_ascii_case()`. This rewrite was proposed 15 times (#450, #453, #457-#460, #466-#472, #478, #479), measured, and rejected: it saves about 12 ns per call, which is about 0.012 ms when listing 1,000 issues, and `track issue search` takes the same 3.2 ms with or without it. The call sites (state mapping on issue update, Linear query parsing, priority colouring) run once per command or once per displayed field, next to network requests that take tens of milliseconds, and the if/else chains are longer and harder to scan than the match tables they replace.

Only propose an allocation or string-matching optimization when a benchmark of a real `track` command shows a difference the user would notice, and put the numbers in the pull request. Before opening a pull request, check the open and recently closed ones for the same change and do not open a duplicate.
